# Contextory metadata reuse and documentation assessment

Read-only assessment, November 23, 2026. Implementation of the UI/recovery work and its background-startup follow-up was completed before this recommendation was finalized. No documentation integration or foreign-project metadata importer was implemented.

**Recommendation: both ideas are feasible and useful.** Reuse an existing project's Contextory knowledge first, then add a source-backed documentation adapter. Keep documentation generation optional and outside service startup. This would help agents recover the reasons and contracts behind code, while the source graph supplies the actual definitions and dependencies.

| Area | Existing foundation | Additional work |
| --- | --- | --- |
| Another project's knowledge | Scoped workspace routing and paginated project exports | Read-only discovery/access for a reference project that is not an active workspace member |
| Existing architecture/mapping | Persistent source graphs, source fingerprints and isolated reference projections | Validate and reuse compatible cached facts; rebuild changed or incompatible facts |
| Natural-language project docs | A structured bilingual corpus, Markdown/LLM exports and read-only query runtime | Connect sections to Contextory record IDs, source symbols and changes |
| Keeping explanations current | Catalog revisions, source freshness, request outcomes and release history | Track affected sections and propose targeted updates for review |

Contextory already embeds part of the documentation plugin **for its own documentation build**. [PROVENANCE.json](../scripts/documentation/vendor/PROVENANCE.json) records a pinned `software-documentation` 1.0.0 copy, and [build.py](../scripts/documentation/build.py) wraps its renderer. This is different from making documentation a capability available to every connected project. The inspected [CustomAgents module](C:/Projetos/CustomAgents/plugins/software-documentation/module.json) is version 1.0.1, requires Carbon design guidance, and uses Python 3.11+ with the standard library. Its current [core runtime](C:/Projetos/CustomAgents/runtimes/documentation/core.py) uses corpus schema version 2; Contextory's current corpus uses version 1. An upgrade needs a deliberate compatibility/migration step rather than a blind replacement.

The plugin already supplies useful pieces: source inventory and fingerprints, reviewed source citations, structured bilingual pages, build verification, migration, Markdown and LLM exports, and portable consumer bundles. Its [read-only library MCP](C:/Projetos/CustomAgents/runtimes/documentation/library_mcp.py) offers `docs_query` and `docs_symbols`; [consumer.py](C:/Projetos/CustomAgents/runtimes/documentation/consumer.py) packages a verified corpus and guidance without requiring the original source project to remain available. The repository has tests for stale builds, tampered artifacts, portable installation and independent consumers. These tests were inspected, not executed during this assessment. The repository license is MIT; bundled IBM Plex fonts retain their separate SIL OFL notices.

For metadata reuse, the current [reference registry](../src/codebase/references.ts:164) deliberately creates a separate projection ledger and a separate `Knowledge` instance. It reads the other project's source, but does not reuse that project's requests, decisions or approved definitions. The [project export API](../src/knowledge/export.ts:20) already exposes records, immutable revisions, history, relationships, source facts and artifacts, with project identity, sequence and snapshot. That is a strong starting point for the missing adapter.

Prefer a read-only connection to the owning project's service when available, or a versioned portable export when it is offline. Retain project/root identity, record revisions, source hashes, snapshot/sequence, export time and approved versus observed versus historical state. A source change should invalidate the affected cached facts or explanations. Keep foreign knowledge explicitly attributed to its project; do not turn it into current-project requirements or grant workflow writes through a read-only reference.

Do not open the other project's database with Contextory's current `Ledger` constructor as a shortcut. [Ledger initialization](../src/storage/ledger.ts:21) configures/migrates storage and marks running jobs interrupted. If direct offline SQLite access is eventually supported, it needs a genuinely read-only reader with explicit schema and identity checks and a consistent snapshot. It must not migrate, repair or modify the owner's live database.

I would deliver this in three steps:

1. **Reuse knowledge from reference projects.** Add an explicit read-only metadata source, visible provenance and freshness, and a fallback to source indexing when metadata is missing or incompatible.
2. **Connect a documentation corpus to Contextory retrieval.** Give sections stable IDs and links to catalog entries, source symbols/files, decisions, specs and evidence. Retrieve only relevant sections alongside current source citations. An agent should be able to ask what an area does and why, without loading an entire LLM export into every hook.
3. **Maintain explanations as work changes.** Mark affected sections stale, show proposed updates and before/after content for review, and build/publish only through the appropriate explicit actions. In the UI, put “Explain this area” near a selected architecture/source item and documentation impact near a request/outcome, rather than adding another permanent top-level tab.

The main design risk is conflicting authority, rather than rendering. Code, inferred relationships, reviewed definitions, historical decisions and generated explanations have different meanings. Keep those distinctions visible. A changed file should prompt a targeted documentation review, not silently approve a new requirement. Run rendering/indexing as bounded background work so an optional Python tool or documentation build cannot block the Node service or recreate the startup issue fixed in this delivery.

This is a source-backed feasibility review, not proof of an implemented integration or a complete audit of CustomAgents. The registered read-only CustomAgents reference had a partial index with three large generated catalogs skipped; the relevant runtime, module and contract files were also inspected directly. No CustomAgents source, configuration, ledger, trust settings or installed plugin was changed.
