# Contextory v0.6.0

Keep each project in a multi-folder workspace separate, coordinate requests across selected projects, and let existing native MCP connections recover from delayed Contextory startup.

## Changes

- Add a **Project** selector and project badges on requests and specs. Each folder keeps its own requests, symbols, knowledge, history, versions, checks, sessions and evidence. Duplicate folder names remain distinguishable.
- Select affected projects in **New request** to create linked local request branches. Open each branch from **Across projects**. The aggregate completes only after every local branch completes; missing, offline or removed projects keep it incomplete.
- Retain the original request input for explicit, idempotent recovery after partial creation. Each branch keeps its own milestones, specs, lease and verification; creation is recoverable rather than atomic across repositories.
- Scope native tools with `projectId` and, when needed, `workspaceId`. An omitted/current project always means that native server's own project, regardless of UI selection or earlier calls. Peer routing verifies identity and preserves native roles. Read-only `codebaseId` references remain separate from writable workspace members.
- Add `contextory_workspace_get`, `contextory_workspace_request_create`, CLI `projects [group-id]` and `--project`/`--workspace` flags. Update shared instructions and portable skills.
- Use folder-specific startup preferences, checks and source navigation. Cursor traces and unsaved overlays follow the actual source folder. Removing and re-adding a folder preserves its existing storage and records.
- Clear project-specific UI state on switching and reject delayed replies, including old dashboard restores after the new project has loaded.
- Keep MCP discovery available while a managed native proxy retries delayed service readiness in the background for up to **five minutes**. Each foreground readiness wait stays bounded to fifteen seconds. Mutations are dispatched once and are never automatically replayed.

See the [commit comparison](https://github.com/igormicadei/Contextory/compare/v0.5.1...v0.6.0), [multi-project guide](../USER-GUIDE.md#multiple-projects-in-one-workspace) and [connection recovery](../USER-GUIDE.md#resume-an-existing-chat).

## Install or upgrade

1. Use Windows, Node.js **24+**, and VS Code **1.96+** or IBM Bob. Open a trusted local folder or a workspace with separate, non-nested project folders.
2. Download `contextory-workspace-0.6.0.vsix` and `contextory-workspace-0.6.0.sha256` from the [GitHub release](https://github.com/igormicadei/Contextory/releases/tag/v0.6.0). Compare the VSIX SHA-256 with the checksum file.
3. Choose **Extensions > Install from VSIX**, select the package and reload when prompted. VS Code users can run `code --install-extension .\contextory-workspace-0.6.0.vsix`.
4. After the managed tool catalog changes, use **Contextory: Restart Agent Extensions** or the native client's MCP reload control. Resume/reopen an older chat if it still advertises the previous tools. Native project and hook trust remain client-owned.
5. Choose the intended project in Contextory. In native chat, ask the agent to discover workspace membership and carry explicit project scope through related operations.

Existing single-folder records and client configuration are preserved. Removing a workspace folder does not delete its records. The five-minute readiness recovery handles an already-configured native connection starting before the service; it does not approve hooks or force every existing chat to discover new tools.

## Validation and limits

Qualification includes **97 backend tests**, **35 UI tests**, typechecking, native/headless transport and registration checks, portable-resource validation and the complete documentation build. The extracted package is exercised in disposable VS Code and IBM Bob profiles with two project folders. See the [validation record](../VALIDATION.md).

Up to sixteen separate local project roots are accepted. Nested/remote roots, other operating systems, authenticated native-agent conversations and large-workspace performance remain unqualified. Static diagrams show possible bounded paths. Each cross-project branch requires independent local completion; there is no shared lease or atomic repository-wide transaction. Distribution uses GitHub release assets; the project remains **UNLICENSED**.
